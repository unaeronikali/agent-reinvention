NorthStar Digital Twin

Fundamentals · 20 min

What we are building

You’re building a Digital Twin of NorthStar Retail’s Azure cloud — a live dashboard of 2 resource groups and 8 resources. Inject one of 5 fault scenarios and a team of 7 AI agents detects it, diagnoses the root cause, proposes a fix, and (with your approval) applies it and files a real ServiceNow ticket. This tab names the seven building blocks you’ll work with — what each is and why it’s here.

01

Python + FastAPI Backend & the brain

Python is the language the backend is written in. FastAPI is the web framework that turns Python functions into HTTP endpoints. In this app FastAPI does double duty: it serves the REST API and it is the Executor — the loop that drives the agents. It’s async, which matters because the agent loop spends most of its time waiting on slow model calls.

Analogy FastAPI is the building’s front desk and its operations manager: it answers the phone (HTTP) and also walks the incident from team to team behind the scenes.

02

SQLite The local database

A zero-setup database that lives in a single file (backend/northstar.db). It stores everything the twin knows: the resource groups and resources, their time-series metrics, the fault scenarios, and each live incident with its activity log. Nine tables in total — the schema is pre-shipped in schema.sql and is a frozen contract.

Key idea The seed script writes raw metric values only — it never marks anything as an anomaly. Deciding what’s abnormal is the Detect agent’s job. The data is just data; the intelligence lives in the agents.

03

MCP Model Context Protocol

A standard way to expose tools (functions an AI can ask to run) behind a small server. Here an MCP server declares 6 tools — read metrics, read thresholds, run RCA, suggest a fix, apply a fix, create a ServiceNow ticket. The agents never call these directly; the Executor (the MCP client) does, on their behalf. MCP is the pre-shipped part — you’ll build the client.

Analogy MCP is a wall of labelled buttons. The agents can point at a button; only the Executor is allowed to press it.

04

Azure AI Foundry Where the agents live

The cloud service that hosts the 7 agents. Each agent is just a system prompt you author in the Foundry portal. Your app talks to them by name over keyless Azure AD auth (you sign in once with az login — there is no API key). The agents are deliberately blind and stateless — see the next tab.

05

Server-Sent Events SSE · the live feed

A one-way stream from server to browser. As the Executor drives the incident, it emits events — a log line, a canvas glow, a status change, a Human-in-the-Loop pause — and the UI reacts in real time. SSE is server→client only; when a human approves a fix or submits a ticket, that goes back the other way as a normal REST POST.

06

React + Vite + TypeScript The frontend

React builds the UI from components; Vite is the dev server that hot-reloads them; TypeScript adds types so mistakes surface before you run. The Vite dev server proxies /api/* to the backend on port 8000, so the browser only ever talks to one origin.

07

React Flow The orchestration canvas

A library for node-and-edge diagrams. It draws the hub-and-spoke canvas: the Executor in the centre, the Orchestrator and 6 agents around it, the MCP server off to the side. As the incident runs, the active block and line glow red. The canvas is pre-shipped — its node IDs are wired to the backend, so it’s the one piece you don’t rebuild by hand.

Agentic · 20 min

Blind agents and the hub that carries them

This app is a multi-agent system with one unusual, deliberate constraint. Understanding that constraint is the whole point of the session — it’s why MCP and the Executor exist. Read this tab before you build.

01

Agent Model + loop + tools

An agent is a language model wrapped in a loop that lets it take actions: read something, decide, act, read the result, decide again. Our seven agents each own one step of incident response: Detect, Analyze, RCA, Suggest, Fix, Ticket, plus an Orchestrator that routes between them.

02

The core constraint Blind & stateless

Each Azure Foundry agent knows only three things per turn: (1) its own system prompt, (2) the JSON payload the app feeds it this turn, and (3) a menu of allowed tool names and agent names. It cannot touch the database, run a tool, or call another agent. It can only read the payload and emit one JSON decision:

an agent’s only three possible outputs 
{ "decision": "use_tool", "tool": "run_rca",  "reason": "…" }
{ "decision": "handoff",  "agent": "Analyze", "reason": "…" }
{ "decision": "none",                          "reason": "…" }

Why on purpose? The ideal would be Claude Code with local .claude/agents that have native DB and tool access. But most participants don’t have that, so we use portable Foundry agents — at the cost of being blind. That cost is the teaching opportunity.

03

The “middle thing” The Executor / MCP client

If agents can’t touch anything, someone must. That someone is the Executor — the backend loop that sits between every agent↔agent and every agent↔tool interaction. It builds each agent’s JSON payload, reads the agent’s decision, and then actually performs it: routes to the next agent, or calls the MCP tool and feeds the result back. It holds the database, and it streams every step to the UI. There is always a middle thing — and MCP is what standardises it.

04

The incident flow Detect → … → Resolved

Every hop passes through the Executor hub. The status of the incident tells you which agent is active:

StatusActive agentCanvas
DETECTINGDetect — scans metrics vs thresholds🔴 glow
ANALYZINGAnalyze — pinpoints the resource + metric🔴 glow
DIAGNOSINGRCA — traces root cause + cascade🔴 glow
AWAITING_FIX_APPROVALSuggest done — HITL #1🔴 slow throb
FIXINGFix — applies the approved fix🔴 glow
AWAITING_TICKET_APPROVALTicket draft — HITL #2🔴 slow throb
RESOLVEDAll idle; ServiceNow ticket created✅ dim
05

Human-in-the-Loop Two real pauses

The flow genuinely stops and waits for a human twice. At HITL #1 the Suggest agent presents fix options and the loop parks until you pick one and click Apply Fix. At HITL #2 the Ticket agent drafts a full description and the loop parks until you review, edit, and click Submit Ticket. Under the hood the loop is literally awaiting an asyncio.Future that your REST POST resolves — the agents cannot proceed without you.

06

The 6 MCP tools Data in, actions out

ToolWhat it does
get_resource_metricsRead current simulated metrics from the DB
get_thresholdsReturn normal/warning/critical reference data for the Detect agent to reason over
run_rcaIdentify root cause from metric patterns + cascade across siblings
suggest_fixPropose remediation options for the abnormal metrics
apply_fixSimulate the fix — write healthy values back, mark the resource Healthy
create_servicenow_ticketPOST the incident to your ServiceNow PDI

Remember Tools only supply data or perform actions. They never decide what’s an anomaly and never write is_anomaly — that’s the Detect agent’s call, written by the Executor.

ServiceNow

Get your ServiceNow PDI

The Ticket agent files a real incident in a ServiceNow Personal Developer Instance (PDI) — a free, personal ServiceNow environment. Set this up before the session and drop the credentials into your .env.

01

Create a developer account One-time

Go to developer.servicenow.com and sign up (free). Verify your email and sign in.

02

Request a Personal Developer Instance PDI

In the developer portal, open the account menu and choose Request Instance. Pick the most recent release. After a minute you’ll get an instance URL like https://dev123456.service-now.com plus an admin username and a generated password.

03

Retrieve your credentials URL · user · password

From Manage instance password in the portal, copy the three values you need. The app authenticates to the ServiceNow Table API with HTTP Basic auth using these.

  • SN_INSTANCE — the full URL, e.g. https://dev123456.service-now.com
  • SN_USER — the admin username (often admin)
  • SN_PASSWORD — the instance password
04

Keep your instance awake Hibernation

PDIs hibernate after a few hours of inactivity. If ticket creation fails with a connection error during the session, open your instance URL in a browser to wake it up, then retry. Log in the morning of the session to be safe.

05

Put the values in .env Final step

In the project root, add your three values to .env (copied from .env.example). The default target table is incident — leave SN_TICKET_TABLE unset unless you know you need a different one.

01

Data layer — db.py SQLite access

Build the one module that every other module uses to touch the database. No raw SQL will live anywhere else. The schema is pre-shipped in backend/schema.sql.

prompt — paste into your AI assistant
First read backend/schema.sql so you know the exact 9 tables and columns. Then build
backend/db.py as the SINGLE SQLite access layer for this project. No other module may
run raw SQL — everything goes through functions here.

CONVENTIONS
- Module constants: BASE_DIR (this file's directory), DB_PATH = <BASE_DIR>/northstar.db,
  SCHEMA_PATH = <BASE_DIR>/schema.sql.
- _now() -> str: ISO-8601 UTC, seconds precision (e.g. "2026-08-24T14:03:07+00:00").
  Use it for EVERY datetime column written.
- get_connection() opens DB_PATH, sets row_factory = sqlite3.Row and
  PRAGMA foreign_keys = ON. Open a FRESH connection per function call and close it in a
  finally block (so functions are safe to call from asyncio.to_thread). Do not cache a
  module-level connection.
- Every row-returning function returns a plain dict (or list[dict]) — never sqlite3.Row.
  Add small _row_to_dict / _rows_to_dicts helpers.

LIFECYCLE
- init_db(schema_path=SCHEMA_PATH): executescript the schema file (it is idempotent —
  it DROPs then CREATEs). reset_db(): delete the northstar.db file if it exists, then init_db().

CRUD HELPERS (create these; names and params matter — later phases call them exactly):
- resource_groups: insert_resource_group(name, description=None) -> int;
  get_resource_groups(); get_resource_group(id); get_resource_group_by_name(name).
- resources: insert_resource(resource_group_id, name, type_, display_name=None, icon=None,
  status="Healthy") -> int (stamp status_updated_at=_now()); get_resources(resource_group_id=None);
  get_resource(id); get_resource_by_name(name); update_resource_status(resource_id, status)
  (also re-stamp status_updated_at).
- resource_metrics: insert_resource_metric(resource_id, metric_name, value, unit=None,
  recorded_at=None, is_anomaly=None) (recorded_at defaults to _now());
  get_resource_metrics(resource_id=None, metric_name=None) ORDER BY recorded_at, id;
  get_latest_metrics(resource_id=None) — the most recent row per (resource_id, metric_name)
  via a join on MAX(recorded_at); set_metric_anomaly(metric_id, is_anomaly) — the ONLY
  function that writes is_anomaly; clear_resource_metrics(resource_id=None);
  get_metric_history(resource_id, minutes=15) -> {metric_name: [{recorded_at, value, unit}]}
  (only rows newer than now - minutes, each list ascending); prune_resource_metrics(older_than_minutes=15)
  -> int rows deleted. For the time-window queries compare recorded_at as a STRING against an
  ISO cutoff string built the same way as _now() (no per-row date parsing).
- thresholds: insert_threshold(resource_id, metric_name, normal_min, normal_max, warning_value,
  critical_value, comparison, unit=None); get_thresholds(resource_id=None, metric_name=None);
  get_threshold(resource_id, metric_name).
- scenarios: insert_scenario(scenario_id, name, description, affected_resource_id, severity) -> int
  (insert an EXPLICIT id, 1-5); get_scenarios() ORDER BY id; get_scenario(id).
- scenario_metrics: insert_scenario_metric(scenario_id, resource_id, metric_name, injected_value,
  unit=None); get_scenario_metrics(scenario_id).
- incidents: create_incident(scenario_id, resource_id, status="DETECTING") -> int — FIRST set
  is_active=0 on any currently-active incident, THEN insert the new one with is_active=1,
  detected_at=_now() (this enforces "single active incident"); get_active_incident();
  get_incident(id); get_incidents() ORDER BY id DESC; update_incident_status(id, status);
  update_incident_rca(id, rca_summary); update_incident_ticket_draft(id, draft);
  update_incident_ticket_final(id, final); resolve_incident(id, servicenow_ticket_no=None) —
  status='RESOLVED', resolved_at=_now(), is_active=0, keep existing ticket no if new is None;
  deactivate_incident(id).
- incident_fixes: insert_incident_fix(incident_id, description, display_order) -> int (is_selected=0);
  get_incident_fixes(incident_id) ORDER BY display_order, id;
  select_incident_fix(fix_id) — clear is_selected on all fixes of that incident, set 1 on this one.
- agent_activity: insert_agent_activity(incident_id, agent_name, message_type, message) -> int
  (created_at=_now()); get_agent_activity(incident_id=None) ORDER BY created_at, id.

INVARIANT: nothing here ever sets is_anomaly except set_metric_anomaly. Do not derive status
from metrics here — status is written explicitly by update_resource_status.

02

Seed script — seed.py The fault injector

One script, two modes. --mode normal rebuilds the DB with all static data plus healthy metrics; --mode anomaly --scenario N injects one scenario’s bad values. The exact seed data is below — it must match precisely, because the agents and thresholds reason over it.

prompt — paste into your AI assistant
Build backend/seed.py. It uses backend/db.py only (no raw SQL). Two modes via argparse:
  --mode {normal,anomaly}   (required)
  --scenario {1,2,3,4,5}    (int; REQUIRED when mode=anomaly — enforce with parser.error)

FUNCTIONS
- _is_static_seeded() -> bool: True if db.get_resource_groups() is non-empty; catch
  sqlite3.OperationalError (no tables yet) and return False.
- seed_static_data(): insert all static rows below, in this order: resource_groups, resources,
  thresholds, scenarios, scenario_metrics. Build name->id maps as you go to resolve foreign keys.
- seed_normal(): db.reset_db(); seed_static_data(); random.seed(42); then for EACH resource and
  EACH of its thresholds, insert one resource_metric with
  value = round(random.uniform(normal_min, normal_max), 2), is_anomaly left None; finally
  update_resource_status(resource_id, "Healthy") for every resource.
- seed_anomaly(scenario_id): if NOT _is_static_seeded(): db.init_db() + seed_static_data()
  (note: init_db, NOT reset_db — never wipe here). Validate the scenario exists (else print an
  error mentioning "Valid range is 1-5" to stderr and sys.exit(1)); validate it has
  scenario_metrics rows (else error + exit). For each scenario_metric, insert a resource_metric
  with value = injected_value, is_anomaly None, printing "- <resource>.<metric> = <value> <unit>".
- main(): parse args and dispatch.

HARD INVARIANT: seed.py NEVER sets is_anomaly (that is the Detect agent's job). anomaly mode
never wipes data and never changes resources.status.

03

MCP client — mcp_client.py Calls the 6 tools

The MCP server is pre-shipped in mcp-server/server.py. You build the client that spawns it as a subprocess and calls its tools. You never run the server by hand — the client launches it over stdio.

prompt — paste into your AI assistant
First read mcp-server/server.py to see the 6 tool names, their arguments, and their return
shapes. Then build backend/mcp_client.py — the async MCP client (the ONLY caller of those tools).

Use the `mcp` Python SDK (stdio transport):
- Paths: BASE_DIR = this file's dir; PROJECT_ROOT = parent; SERVER_SCRIPT =
  PROJECT_ROOT/mcp-server/server.py.
- _get_session() -> ClientSession: lazy singleton guarded by an asyncio.Lock. On first call,
  verify SERVER_SCRIPT exists (else RuntimeError), open an AsyncExitStack, create
  StdioServerParameters(command=sys.executable, args=[str(SERVER_SCRIPT)]) so the server runs in
  the SAME Python interpreter, enter stdio_client(params) to get (read, write), enter
  ClientSession(read, write), await session.initialize(), and cache both the session and the
  exit stack at module scope.
- close(): aclose the exit stack and reset the singletons (call this on app shutdown).
- _call_tool(name, arguments) -> dict: result = await session.call_tool(name, arguments);
  concatenate the .text of each content block; if result.is_error raise RuntimeError(text);
  if there is no text return {}; else json.loads(text).
- One async function per tool, each building an `arguments` dict that OMITS any None optional,
  then returning _call_tool(name, arguments):
    get_resource_metrics(resource_id=None)
    get_thresholds(resource_id=None, metric_name=None)
    run_rca(incident_id=None, resource_id=None)
    suggest_fix(incident_id=None, resource_id=None)
    apply_fix(resource_id, incident_id=None, fix_description=None)
    create_servicenow_ticket(short_description, description, urgency=None, category=None, incident_id=None)

Tool errors (including "ServiceNow not configured") come back as is_error results whose message
you re-raise as a plain RuntimeError, so the executor/UI can show it.

Executor — executor.py The hub / agent loop

The heart of the app. It prompts each blind agent, reads its JSON decision, and performs it — routing to the next agent or calling an MCP tool and feeding the result back. It writes the DB, streams SSE, and blocks on the two HITL pauses. Read af-agents/README.md (payload/decision contract) and frontend/src/Canvas.tsx (node/edge IDs) before building.

prompt — paste into your AI assistant
Read af-agents/README.md and frontend/src/Canvas.tsx first. Then build backend/executor.py —
the hub that drives one incident from DETECTING to RESOLVED. It uses db.py and mcp_client.py.

CONSTANTS
- TOOLS = {"get_resource_metrics","get_thresholds","run_rca","suggest_fix","apply_fix","create_servicenow_ticket"}
- AGENTS = {"Orchestrator","Detect","Analyze","RCA","Suggest","Fix","Ticket"}
- _AGENT_ENV maps each agent name to its env var: Orchestrator->ORCHESTRATOR_AGENT, Detect->DETECT_AGENT,
  Analyze->ANALYZE_AGENT, RCA->RCA_AGENT, Suggest->SUGGEST_AGENT, Fix->FIX_AGENT, Ticket->TICKET_AGENT.
- MAX_STEPS = 40; token scope "https://ai.azure.com/.default"; default model "gpt-5".

SSE BROKER (in-process pub/sub)
- subscribe() -> asyncio.Queue; unsubscribe(q); async emit(event_type, data): put
  {"type": event_type, "data": data} on every subscriber queue (skip on QueueFull).

FOUNDRY CALL — async call_af_agent(agent_name, payload) -> dict (run the sync body in
asyncio.to_thread). Inside: read the agent NAME from os.getenv(_AGENT_ENV[agent_name]); require
FOUNDRY_ENDPOINT. Use azure-ai-projects: AIProjectClient(endpoint, DefaultAzureCredential()).
get_openai_client(agent_name=<NAME>), then client.responses.create(model=<model>,
input=json.dumps(payload)); read resp.output_text. The model MUST equal the agent's own model —
resolve it as FOUNDRY_MODEL override, else auto-detect from the project, else "gpt-5". Cache the
project client, credential, and openai clients as module singletons behind a lock. Import azure-*
lazily inside the client factory so the module imports without azure installed (headless tests
monkeypatch call_af_agent).
Parse the reply with _parse_decision: strip ``` fences and an optional leading "json"; json.loads;
require a dict with "decision" in ("use_tool","handoff","none"); if use_tool, "tool" must be in
TOOLS; if handoff, "agent" must be in AGENTS; else raise RuntimeError.

CANVAS PAYLOAD — _canvas_payload(incident_id, node, mode, status) ->
{"incident_id","active_node","active_edge","mode","status"}. active_edge: if node in
("Executor","MCP") -> {"from":"Executor","to":"MCP"}; if node in AGENTS -> {"from":node,"to":"Executor"};
else None. Node names, edge from/to, and modes ("glow","slow_throb","idle") must match Canvas.tsx.

RUN STATE — class IncidentRun(incident_id, auto_approve=False) holding: status="DETECTING",
handoff_from=None, ticket_submitted=False, anomaly_persisted=False, context={}, fix_future,
ticket_future, done=asyncio.Event(), finished_status. Track one active run in a module global;
get_current_run().

THE LOOP _drive(run): start current_agent="Detect", tool_result=None, steps=0. While steps < MAX_STEPS:
  1) payload = _build_payload(run, current_agent, tool_result)
  2) emit canvas glow for current_agent
  3) emit an INFO activity "start line" naming the agent (do this BEFORE the slow model call so the
     canvas glow and newest log line agree)
  4) decision = await call_af_agent(current_agent, payload); _ingest(run, current_agent, decision)
  5) emit decision["reason"] as an INFO activity line; reset tool_result=None
  6) branch on decision["decision"]:
     - "use_tool": tool_result = await _run_tool(run, current_agent, decision["tool"]); continue
       (feed result back to the SAME agent next turn)
     - "handoff": run.handoff_from = current_agent; if the next agent maps to a status
       (Analyze->ANALYZING, RCA->DIAGNOSING, Fix->FIXING) set it; current_agent = decision["agent"]
     - "none": token = await _handle_none(run, current_agent); RESOLVED->return;
       RESUME_FIX->current_agent="Orchestrator"; RESUME_TICKET->current_agent="Ticket"

_build_payload(run, agent, tool_result): base {"incident_id","status"} plus per-agent fields drawn
from run.context, exactly as af-agents/README.md specifies (Detect: metrics+thresholds; Orchestrator:
handoff_from+anomalies+context subset; Analyze: handoff_from+anomalies; RCA: affected_resource+tool_result;
Suggest: affected_resource+rca+tool_result; Fix: affected_resource+selected_fix+tool_result; Ticket:
severity, detected_at, resolved_at, affected_resource, anomalies, rca, fix_result, submit_approved,
ticket_final, tool_result). IMPORTANT: the Ticket payload's submit_approved MUST be run.ticket_submitted
(which _handle_none sets True right after the human submits at HITL #2) — NOT a context key. If it is
wired to a never-written context flag it stays False, so the Ticket agent keeps re-drafting instead of
calling create_servicenow_ticket, and the incident resolves with no ticket.

_ingest(run, agent, decision): write the agent's output into run.context and the DB — Detect:
context["anomalies"]=decision["anomalies"], and the FIRST time only, persist is_anomaly via
_persist_anomalies and re-derive the resource status; Analyze: context["affected_resource"]; RCA:
context["rca"]+rca_summary and db.update_incident_rca; Suggest: context["fix_options"] and, if none
exist yet, db.insert_incident_fix per option; Fix: context["fix_result"]; Ticket:
context["ticket_draft"] + db.update_incident_ticket_draft, and context["ticket_number"] when present.

_run_tool(run, agent, tool): emit a "tool" call event + canvas MCP glow, dispatch to the matching
mcp_client.* function, store results into context (get_resource_metrics->detect_metrics,
get_thresholds->detect_thresholds, run_rca, suggest_fix, apply_fix, create_servicenow_ticket). For
apply_fix, after it succeeds call sampler.set_normal(resource_id) BEFORE re-deriving status; for
create_servicenow_ticket build short/description from context and store the ticket number. Emit a
"tool" result event and return the result.

HITL (real blocking): _await_fix_approval(run) — if auto_approve return the first fix id, else
create run.fix_future and await it. _await_ticket_submission(run) — if auto_approve return the draft,
else await run.ticket_future. Public resolvers called by the API: provide_fix_approval(incident_id,
fix_id) and provide_ticket_submission(incident_id, ticket_final) — verify the current run matches and
its future is pending, then set_result and return True (else False).

_handle_none(run, agent): if agent=="Suggest": set status AWAITING_FIX_APPROVAL, canvas Suggest
"slow_throb", emit an "hitl" #1 event whose fix_options are the STORED db.get_incident_fixes(incident_id)
rows (each {id, display_order, description}) — NOT the raw agent options, because the DB id is what the
frontend selects and the /api/hitl/fix POST references. Then await fix approval, db.select_incident_fix,
store selected_fix, log a HUMAN activity line, set handoff_from="Suggest", return "RESUME_FIX". If
agent=="Ticket" and not yet submitted: set status AWAITING_TICKET_APPROVAL, canvas Ticket "slow_throb",
emit "hitl" #2 with ticket_draft, await submission, store+persist ticket_final, mark submitted, log
HUMAN activity, return "RESUME_TICKET". Otherwise: db.resolve_incident(incident_id, ticket_no),
status RESOLVED, emit "status" + canvas Orchestrator "idle" + a "resolved" event, return "RESOLVED".

HELPERS: _persist_anomalies (the ONLY runtime writer of is_anomaly — set 0/1 per Detect's decision);
_derive_status(resource_id) -> Healthy/Degraded/Critical from thresholds (gt/lt vs
critical_value/warning_value); _update_resource_status.

SSE EVENTS to emit (names + payloads): "activity" {incident_id,id,agent_name,message_type,message,created_at};
"status" {incident_id,status}; "canvas" (the payload above); "resource_status" {incident_id,resource_id,status};
"tool" {incident_id,agent,tool,phase:"call"|"result"[,result]}; "hitl" #1 {incident_id,hitl:1,fix_options:[{id,display_order,description}]}
and #2 {incident_id,hitl:2,ticket_draft}; "resolved" {incident_id,status:"RESOLVED",servicenow_ticket_no};
"error" {incident_id,message}.

ENTRYPOINTS: async run_incident(incident_id, auto_approve=False) -> IncidentRun — wraps _drive in
try/except so a failure logs an ERROR activity + emits "error" + sets finished_status, and ALWAYS
sets run.done. launch_incident(incident_id, auto_approve=False) -> asyncio.Task that runs it — and
STORE that task in a module-level _current_task so it can be cancelled later (a fire-and-forget task
that nobody holds a handle to can never be stopped).

async cancel_current_run(reason="baseline restored") -> Optional[int]: stop the running loop. If
_current_run is None or run.done is already set, return None. Otherwise _current_task.cancel(), then
await the task, swallowing BaseException (CancelledError is a BaseException, and run_incident catches
only "except Exception", so its "finally: run.done.set()" still runs; cancelling also unblocks a loop
parked on run.fix_future / run.ticket_future). Then drive the UI back to idle using ONLY events the
frontend already handles: _activity(run,"Executor","WARNING", f"Orchestration stopped — {reason}.
Incident closed."), emit "canvas" _canvas_payload(run.incident_id,"Orchestrator","idle",run.status),
and emit "resolved" {incident_id:run.incident_id, status:"RESOLVED", servicenow_ticket_no:None} (the
frontend clears the HITL panel ONLY on "resolved"). Finally set _current_run=_current_task=None and
return the incident_id.

FastAPI — main.py REST + SSE + HITL

The HTTP surface the frontend talks to. It exposes read endpoints, fault inject/restore, the two HITL POSTs, and the SSE stream — and on startup it seeds static data (if empty) and launches the background live-metrics sampler (pre-shipped sampler.py).

prompt — paste into your AI assistant
Build backend/main.py — a FastAPI app that is the HTTP surface. It uses db.py, seed.py, sampler.py,
executor.py, mcp_client.py. All business logic lives in the executor; main.py just wires HTTP.

FIRST LINE OF THE MODULE, before anything reads environment variables: load the project-root .env
with python-dotenv so the executor and tools see FOUNDRY_ENDPOINT, the seven *_AGENT names, and the
SN_* values. Use an absolute path so it works regardless of the launch directory:
    from pathlib import Path
    from dotenv import load_dotenv
    load_dotenv(Path(__file__).resolve().parent.parent / ".env")
(Without this, injecting a fault fails with "Missing Detect agent configuration: DETECT_AGENT".)

app = FastAPI(title="NorthStar Retail Digital Twin", version="1.0"). Add CORS from env CORS_ORIGINS
(comma-separated, default http://localhost:5173), allow all methods/headers.

Pydantic bodies: InjectBody{scenario_id:int, auto_approve:bool=False};
FixApprovalBody{incident_id:int, fix_id:int}; TicketSubmitBody{incident_id:int, ticket_final:str}.

ROUTES
- GET /api/health -> {"status":"ok"}
- GET /api/resources -> {"resource_groups":[{...group, "resources":[{...resource,
  "metrics":[{metric_name,value,unit,recorded_at,is_anomaly}]}]}]}. Metrics = latest row per
  (resource_id, metric_name).
- GET /api/resources/{resource_id}/history?minutes=15 -> {resource_id, window_minutes,
  metrics:{name:[{recorded_at,value,unit}]}, thresholds:{name:{normal_min,normal_max,warning_value,
  critical_value,comparison,unit}}}
- GET /api/scenarios -> {"scenarios": db.get_scenarios()}
- GET /api/incident/active -> {"incident": None} or a detail object
  {incident, scenario, resource, activity, fixes}
- GET /api/incident/{id} -> the same detail object, or 404
- GET /api/activity?incident_id= -> {"activity": db.get_agent_activity(incident_id)}
- POST /api/fault/inject (InjectBody): validate scenario_id in 1..5 (400) and exists (404);
  affected_id = scenario["affected_resource_id"]; sampler.set_faulted(affected_id, scenario_id);
  await sampler.sample_once(affected_id); incident_id = db.create_incident(scenario_id, affected_id);
  executor.launch_incident(incident_id, auto_approve=body.auto_approve);
  return {incident_id, scenario_id, status:"DETECTING"}
- POST /api/fault/restore: FIRST await executor.cancel_current_run("operator clicked Restore Normal")
  to STOP any running orchestration loop before touching data — otherwise the loop keeps glowing the
  canvas / advancing activity (and its HITL panel stays live) for an incident you just closed; THEN
  sampler.set_all_normal(); deactivate any active incident;
  return {status:"ok", message:"Baseline restored to healthy."}
- POST /api/hitl/fix (FixApprovalBody): executor.provide_fix_approval(...); 409 if not currently
  waiting; else {status:"ok", resumed:True}
- POST /api/hitl/ticket (TicketSubmitBody): executor.provide_ticket_submission(...); 409 if not
  waiting; else {status:"ok", resumed:True}
- GET /api/stream -> an SSE EventSourceResponse (use sse-starlette). First yield event "connected"
  with data {active_incident: db.get_active_incident()} (the RAW incident row or null). Then loop:
  subscribe to executor's broker, wait up to 15s for the next event and yield
  {"event": ev["type"], "data": json(ev["data"])}; on timeout yield event "heartbeat" data "{}".
  Unsubscribe on disconnect. Serialize with json.dumps(default=str).

LIFECYCLE
- startup: if not seed._is_static_seeded(): db.init_db() + seed.seed_static_data() (via to_thread);
  then create the background task sampler.run_sampler().
- shutdown: cancel the sampler task; await mcp_client.close().
Run with uvicorn on host 0.0.0.0, port int(os.getenv("PORT","8000")).
